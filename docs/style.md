# Writing style

Use the [Australian Government Style Manual](https://www.stylemanual.gov.au) for all wording owned by this project. This includes menu labels, status messages, alerts, permission messages, documentation and release notes.

## Language and structure

Use [plain language and active voice](https://www.stylemanual.gov.au/writing-and-designing-content/clear-language-and-writing-style). Address the reader as ‘you’. Prefer short sentences and explain technical terms when readers need them.

Use Australian English. Follow the [spelling guidance](https://www.stylemanual.gov.au/grammar-punctuation-and-conventions/spelling), with the Australian concise Oxford dictionary as the reference for variable spellings. Use ‘recognise’, ‘serialise’, ‘behaviour’ and ‘licence’ as a noun.

Use sentence case for menu labels and [headings](https://www.stylemanual.gov.au/structuring-content/headings). Keep brand names, product names, file paths and code identifiers unchanged.

Introduce [lists](https://www.stylemanual.gov.au/structuring-content/lists) with a heading or lead-in. Keep items parallel. For sentence fragments, start with lower case and place a full stop after the final item.

Use descriptive link text. Keep technical detail in sections where readers need it to build, test or troubleshoot the app.

## App wording

Use consistent labels: ‘Noise cancelling’, ‘Ambient sound’, ‘Transparency’, ‘Off’, ‘Focus on voices’ and ‘Open at login’.

Write ‘headphones’ for the general device category. Write ‘Nothing and CMF’ in prose. Spell out ‘Left’, ‘Right’ and ‘Case’ in battery labels. Use ‘Unknown’ for missing readings.

Error messages should explain what happened and give a practical next step where one is available. Avoid raw protocol terms in ordinary controls.

Use minimal punctuation. Where a sentence needs a dash, use a [spaced en dash](https://www.stylemanual.gov.au/grammar-punctuation-and-conventions/punctuation/dashes). Preserve exact third-party notices, quoted material, code and protocol values.

## Review before release

Review every changed string in context. Check clarity, spelling, capitalisation, punctuation, headings, lists and links against the relevant Style Manual guidance.

Keep claims consistent with the evidence. Distinguish simulated tests from tests on physical devices. Do not claim that a successful build establishes accessibility or compatibility with every device.

## README structure and images

Put the purpose, compatibility and installation steps before developer instructions. Use numbered steps for tasks that must happen in order. Keep detailed hardware tests in their own guide.

Follow the Style Manual’s guidance on [plain language and word choice](https://www.stylemanual.gov.au/writing-and-designing-content/clear-language-and-writing-style/plain-language-and-word-choice) and [sentence length](https://www.stylemanual.gov.au/writing-and-designing-content/clear-language-and-writing-style/sentences). Explain unfamiliar terms. Aim for an average of 15 words per sentence and no more than 25.

Use one main heading and do not skip heading levels. Keep headings under 70 characters. Use descriptive links that make sense on their own. Prefer prose or lists when a table adds no useful comparison.

The README header is decorative. Give it an empty alt attribute and keep all essential information in text. Use a `picture` element so GitHub does not turn the image into an unnamed link. Record the image source and generation prompt with the artwork. Check the rendered image and text at desktop and mobile widths.

Review against the Style Manual’s [image guidance](https://www.stylemanual.gov.au/content-types/images) and [alt text guidance](https://www.stylemanual.gov.au/content-types/images/alt-text-captions-and-titles-images). A documentation review does not certify the accessibility of GitHub or the app.
